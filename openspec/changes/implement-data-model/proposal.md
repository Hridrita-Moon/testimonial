# Proposal

## Why

The Testimonial SaaS MVP needs a single, agreed persistence layer before any feature work (spaces, testimonials, wall of love, embed, billing) can land. Today `prisma/schema.prisma` is a working scaffold (init migration applied to `prisma/dev.db`) but it is missing five decisions that came out of the design interview documented in `data-model.md` §13: the `Subscription` row is not uniquely constrained per user, `cancelAtPeriodEnd` is absent, `EmbedConfiguration` is not 1:1 per space, and two read-path indexes are missing. Without these, the public submit, Stripe webhook, and embed endpoints have no safe foundation.

## What Changes

- Add `Subscription.@@unique([userId])` and `Subscription.cancelAtPeriodEnd Boolean @default(false)` so Stripe webhooks can re-apply state idempotently and the "cancel at period end" semantics are honored.
- Add `EmbedConfiguration.@@unique([spaceId])` so each space has exactly one embed config; the embed JS snippet is keyed by the embed config id.
- Add `Testimonial.@@index([spaceId, submissionTimestamp])` to support inbox and chart queries.
- Add `Testimonial.@@index([spaceId, isWallOfLove, visibilityStatus])` to support the public Wall of Love fetch by embed.
- Add `SpaceField.@@index([spaceId, displayOrder])` to support form-config render in display order.
- Bring `prisma/schema.prisma` into full alignment with `data-model.md` (column shape, defaults, relations, indexes) and regenerate the Prisma client.
- Add a migration that applies the five schema changes to the dev database. A reset/seed for the §12 sample data walkthrough is out of scope for this change and will be a follow-up.

No tables added or removed. No columns renamed. The init migration history is preserved; this change adds a single new migration.

## Capabilities

### New Capabilities

- `data-model`: The persisted schema for the Testimonial SaaS MVP. Owns the six tables (`User`, `Space`, `SpaceField`, `Testimonial`, `Subscription`, `EmbedConfiguration`), the relations and indexes between them, and the data invariants documented in `data-model.md` (uniqueness, required fields, allowed enum-like values, ordering and search behavior). This is the foundation capability that every other feature capability (spaces CRUD, public submit, wall of love, embed, billing) will depend on.

### Modified Capabilities

None. There are no existing capabilities yet; this change introduces the first one.

## Impact

- `prisma/schema.prisma` — schema definition edited in place.
- `prisma/migrations/` — one new migration directory added under the existing init migration; the lock file is touched.
- `prisma/dev.db` — dev SQLite database is updated by the migration. The dev DB is not committed; it is regenerated by `prisma migrate dev`.
- `@prisma/client` — regenerated by `prisma generate`; downstream code that imports from `@prisma/client` continues to type-check (no breaking column renames).
- Stripe webhook code (future, not in this change) gains a safe `findUnique by userId` target.
- Public embed endpoint (future) is keyed off `EmbedConfiguration.id`, not `Space.id`.
- All read paths listed in `data-model.md` §6, §7, §8 are supported by the new indexes.
